# commit: 会話コンテキストを考慮したコミット作成

以下のステップを**順番に**実行する。各ステップの判断基準・コマンドは固定なので、モデルによらず同じ手順になるようにすること。

## 1. ブランチ確認

```bash
git branch --show-current
```

- 出力が `main` または `master` の場合:
  1. `git status` と `git diff` の内容から適切なブランチ名を提案する（例: `feat/add-fish-alias`, `fix/nvim-config`）
  2. ユーザーに提案したブランチ名を提示し、承認を得る
  3. 承認が得られたら `git checkout -b <branch>` を実行する
  4. ユーザーが「mainのまま続行したい」と答えた場合はそのまま次のステップへ進む
- それ以外のブランチの場合はそのまま次のステップへ進む

## 2. 変更内容の確認

```bash
git status
git diff
git diff --staged
```

- ステージングされていない変更がある場合、どのファイルをコミットに含めるかをユーザーに確認する
- 確認が取れたファイルのみを対象にする（`git add -A` を無条件に使わない）

## 3. コミットメッセージの作成

**今回の会話の内容を踏まえて**、Conventional Commits形式でメッセージを作成する:

| プレフィックス | 用途 |
|---|---|
| `feat:` | 新機能 |
| `fix:` | バグ修正 |
| `docs:` | ドキュメントのみの変更 |
| `style:` | コードの動作に影響しない変更（フォーマット等） |
| `refactor:` | バグ修正や機能追加を伴わないコード変更 |
| `test:` | テストの追加・修正 |
| `chore:` | ビルドプロセスやツールの変更 |

- 日本語・英語どちらでもよい。変更内容に対して自然な方を選ぶ
- 本文（body）が必要な場合は「何を」ではなく「なぜ」を書く

## 4. コミット実行

1. コミットメッセージ案をユーザーに提示する
2. 承認を得てから対象ファイルを `git add <file...>` でステージングする
3. HEREDOCでコミットメッセージを渡してコミットする:

```bash
git commit -m "$(cat <<'EOF'
<type>: <summary>

<body（任意）>
EOF
)"
```

## 検証

コミット後、以下を実行して結果を確認する:

```bash
git log --oneline -1
git status
```

- `git log --oneline -1` に意図したコミットメッセージが表示されること
- `git status` で意図したファイルのみがコミット済みであること（意図しない変更が残っていないこと）
